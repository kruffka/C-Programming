# Preprocessor (препроцессор)

Компилятор ваш файл целиком не видит. Перед ним по тексту проходит препроцессор - программа без всякой жалости к смыслу: копирует один файл в другой, вырезает куски, подставляет одно слово вместо другого. Типов он не знает, переменных не знает, считать ничего не умеет.

```
main.c -> [ препроцессор ] -> main.i -> [ компилятор ] -> main.s -> [ ассемблер ] -> main.o -> [ линковщик ] -> a.out
```

Отсюда и знаменитые ошибки вида "ошибка в строке 3407": вы открываете файл на 40 строк и не понимаете, откуда там 3407. Это препроцессор накопировал вам три тысячи строк из `stdio.h`, и компилятор честно считает их вашими.

Директивы начинаются с `#` и живут каждая на своей строке. Точка с запятой в конце не нужна: `#include <stdio.h>;` выглядит невинно, но после подстановки эта точка с запятой окажется посреди чужого заголовка, и компилятор расстроится.

##  1. <a name='1'></a>Зачем нужен препроцессор

Всё, что от него реально нужно в 99% кода, укладывается в три вещи: подключить чужой код, дать имя константе и выключить кусок кода до сборки.

Посмотреть, что препроцессор сделал с файлом, можно так:
```bash
gcc main.c -E -o main.i
```
Совет: откройте `main.i` хотя бы раз в жизни. Один взгляд на этот файл заменяет полчаса объяснений, что `#include` - это обычный копипаст. Увидите несколько сотен строк, из которых ваших - штук десять.

Флаг `-P` убирает из вывода служебные пометки с номерами файлов и строк. С ним читать намного приятнее, потому что без него половину файла занимает `# 1 "main.c"` и прочая бухгалтерия.

##  2. <a name='2'></a>include

`#include` значит "включить", и включают им заголовочные файлы - те, что с расширением `.h`. Внутри заголовка обычно не код, а объявления: прототипы функций, структуры, константы, макросы. То есть список того, что где-то существует.

Происходит при этом ровно одно действие: препроцессор находит файл и вставляет его содержимое в то место, где стоит директива. Никакого "подключения библиотеки во время работы" нет, это просто текст.

Скобки задают, где искать файл:
```c
#include <stdio.h>       // системные каталоги, обычно /usr/include
#include "my_header.h"   // сначала рядом с текущим файлом, потом в системных
```
На практике правило простое: свои файлы - в кавычках, чужие - в угловых. Разница только в порядке поиска.

Если заголовки лежат в отдельной папке, тащить путь в каждую строчку не надо - папка сообщается компилятору флагом `-I`:
```c
// вместо "include/my_header.h" пишем просто
#include "my_header.h"
```
```bash
gcc prog.c -o prog -I ./include/
```
где `./include/` - папка с `my_header.h`.

Про включение `.c` файлов. Технически можно, иногда так даже делают в маленьких проектах, но в общем случае это плохо: препроцессор ведь копирует текст целиком. Поправили строчку в включаемом файле - надо пересобрать все файлы, которые его включили. Пока проект на 200 строк, разница незаметна, а когда он на 20 тысяч, вы начинаете пить чай, пока идет сборка.

Проще думать так: заголовок - это оглавление, а `.c` - сама книга. Подключаем оглавление, а текст функций линковщик найдет сам. Как именно - разберем на многофайловых проектах.

##  3. <a name='3'></a>define

`#define` - подстановка текста, и ничего больше. Выглядит как объявление переменной, а работает как копипаст: везде, где встретилось имя, препроцессор вставит то, что вы написали.

Капсом имена макросов пишут не по требованию языка, а чтобы отличать их от переменных. Пример в [define.c](src/define.c).

###  3.1. <a name='3.1'></a>Константы

```c
#define K 123

void func() {
    printf("K = %d\n", K); // 123
}

#undef K // а с этого места K больше нет

int main() {
    // printf("K = %d\n", K); // ошибка: K больше не существует
    func();
    return 0;
}
```

Тут стоит сказать честно: в 90% случаев вместо `#define K 123` лучше написать `const int k = 123;` или завести `enum`. У нормальной константы есть тип и адрес, ее видит отладчик, и компилятор может вас поругать за странности. `#define` остается там, где нужна именно подстановка: размер массива, флаг сборки, условие внутри `#if`.

###  3.2. <a name='3.2'></a>Макросы

Макрос - это подстановка с аргументами:
```c
#define MIN(a, b) ((a < b) ? a : b)

MIN(1, 2); // препроцессор сделает ((1 < 2) ? 1 : 2), то есть 1
```
Полезно, быстро, и именно здесь начинаются грабли, на которые наступают все.

Грабли первые, самые популярные - забытые скобки.
```c
#define ADD(a, b) a + b
int a = 5, b = 3;
int c = ADD(a, b);     // 5 + 3 = 8, пока все хорошо
int d = 4 * ADD(a, b); // 4 * 5 + 3 = 23, а ждали 32
```
<details>
<summary>Что тут чинить</summary>
Завернуть в скобки каждый аргумент и все выражение целиком:
```c
#define ADD(a, b) ((a) + (b))
```
теперь `4 * ADD(a, b)` даст честные 32.
</details>
<br>

Вторые грабли похитрее и куда неприятнее: аргумент подставляется столько раз, сколько он встречается в теле.
```c
MIN(func1(), func2()); // ((func1() < func2()) ? func1() : func2()) - функции вызовутся дважды
MIN(i++, 10);          // i увеличится два раза, и потом полвечера искать, откуда дырка в массиве
```
Никакой ошибки компилятор не покажет, программа просто будет работать не так. Поэтому правило простое: хочется функцию - пишите функцию. Макрос оставьте константам, размерам и флагам сборки.

Отдельная история - макрос из нескольких операторов. Его принято заворачивать в `do { ... } while (0)`, иначе вызов ломает `if` без фигурных скобок:
```c
#define MY_MACRO_BAD { statement1; statement2; }
#define MY_MACRO_GOOD do { statement1; statement2; } while (0)

if (condition) MY_MACRO_GOOD; // ок
if (condition) MY_MACRO_BAD;  // раскроется в { ... }; и это syntax error
```
Заодно такой макрос требует точку с запятой, как нормальная функция, и рука не забывает ее ставить.

###  3.3. <a name='3.3'></a>Предопределенные константы

Компилятор подкидывает несколько готовых макросов. В отладке реально выручают вот эти:
- `__LINE__` - номер строки
- `__FILE__` - имя файла
- `__FUNCTION__` - имя функции
- `__DATE__`, `__TIME__` - дата и время компиляции (не запуска!)

В коде это выглядит так ([constants.c](src/constants.c)):
```c
printf("Error at LINE=%d, FILE=%s, function=%s\n", __LINE__, __FILE__, __FUNCTION__);
printf("Compilation time: date=%s, time=%s\n", __DATE__, __TIME__);
```
```bash
Compilation time: date=Oct 21 2026, time=09:59:25
Error at LINE=5, FILE=src/constants.c, function=func
```

И хитрость, которая экономит вечера. Формат `файл:строка` понимает VSCode: по такой строке в терминале можно прыгнуть в код через Ctrl + ЛКМ. Поэтому в логах печатают именно его:
```c
printf("%s:%d\n", __FILE__, __LINE__); // src/constants.c:7
```

##  4. <a name='4'></a>Условная компиляция

Иногда кусок кода надо выбросить еще до сборки. Не "написать `if`, который не выполнится", а чтобы его вообще не было в бинарнике.
```c
#if B == 5
    // попадет в программу, если B определено как 5
#else
    // иначе попадет этот код
#endif
```
`#elif` - это `else if`. `#ifdef X` то же самое, что `#if defined(X)`, а `#ifndef X` - наоборот.

Значение можно задать прямо в коде, а можно снаружи, флагом `-D` (от слова define):
```bash
gcc src/cond.c -o cond -DB=5 -DDEBUG=1
./cond
```

Самая частая ошибка новичка - попробовать проверить обычную переменную:
```c
int x = 5;
#if x == 5   // не сработает
#endif
```
Для препроцессора `x` не существует. Он работает до того, как в программе появится хоть одна переменная. Это же и ответ на вопрос, почему директивы "не выполняются во время работы": они уже давно отработали к моменту, когда вы запускаете `./a.out`.

Главное применение - отладочные печати, которые не должны уехать в релиз:
```c
int sum(int x, int y) {
    int res = x + y;
#ifdef DEBUG
    // этот код скомпилируется только если DEBUG определен
    printf("DEBUG: Value of x = %d\n", x);
    printf("DEBUG: Value of y = %d\n", y);
    printf("DEBUG: Sum calculated as %d\n", res);
#endif
    return res;
}
```
Собрали без `-DDEBUG` - этих строк в бинарнике не осталось совсем. Не "не выполнились", а именно не осталось, ни байта.

Доводят это обычно до макроса, который сам печатает, откуда пришел вызов. Полный пример в [cond.c](src/cond.c):
```c
#define PRINT_DEBUG(format, ...)                                   \
    do {                                                           \
        printf("%s:%d:%s(): " format, __FILE__, __LINE__, __FUNCTION__, ##__VA_ARGS__); \
    } while (0)
```
```c
PRINT_DEBUG("Error: %s\n", message); // точка с запятой обязательна
```
`...` - это переменное число аргументов, а `##__VA_ARGS__` убирает лишнюю запятую, если аргументов не передали. В итоге в логе сразу видно файл, строку и функцию, и искать место ошибки не приходится.

<details>
<summary>Проверьте себя: что напечатает программа?</summary>
```c
#define SQR(x) x * x
printf("%d\n", SQR(2 + 3));
```
Напечатает 11, потому что получится `2 + 3 * 2 + 3`. Ждали 25, а получили 11 - снова те же грабли со скобками.  
Правильно так:
```c
#define SQR(x) ((x) * (x))
```
</details>
<br>

##  5. <a name='5'></a>Защита от повторного включения

Пока проект в одном файле, заголовки никому не мешают. Проблема появляется, когда `test.c` подключает `test.h` и `test2.h`, а `test2.h` тоже подключает `test.h`. Препроцессору все равно, что этот файл уже был: он честно скопирует его второй раз. И компилятор второй раз увидит ту же структуру, обрадуется и начнет ругаться на повторное объявление.

Лечится это тремя строками в начале заголовка - include guard:

```c
// test.h

#ifndef TEST_H
#define TEST_H

// ..
int a; // определение чего-либо
// ..

#endif // TEST_H
```

Работает просто. Первый раз `TEST_H` не определен - содержимое попадает в файл, а заодно определяется `TEST_H`. Второй раз условие ложно, и весь блок пропускается, как будто файла и не было.

```c
// test2.h

#ifndef TEST2_H
#define TEST2_H

#include "test.h" // если test.h уже включали, второй раз ничего не произойдет

// ..

#endif // TEST2_H
```

```c
// test.c

#include "test.h"
#include "test2.h"

// ..
```

Имя внутри `#ifndef` берут по имени файла, чтобы не столкнуться с чужим заголовком. Старый код любит начинать его с подчеркивания (`_TEST_H_`), но так делать не стоит: имена с подчеркивания и заглавной буквы зарезервированы под систему.

Есть вариант короче, и в новом коде он попадается чаще:
```c
#pragma once
```
Одна строка вместо трех. Минус тоже один: это не стандарт языка, а расширение компиляторов. Но gcc, clang и MSVC его понимают, так что живем. В многофайловых проектах встретите оба варианта, и оба будут работать.


##  6. <a name='6'></a>Итого: препроцессор общается с компилятором

Если из всей лекции запомнить одну мысль, пусть будет эта: **препроцессор разговаривает с компилятором, а не с вашей программой.** Все директивы отрабатывают один раз, до того как появится первая строка машинного кода. К моменту запуска `./a.out` их там уже давно нет.

Отсюда следуют вещи, которые поначалу удивляют:

- в готовом бинарнике нет ни `#include`, ни `#define`, ни `#if`. Есть только результат: подставленные значения и выбранные ветки кода;
- `#if` не может смотреть на переменные - переменных еще не существует, есть только текст;
- `#define K 123` не занимает память, у него нет адреса и типа. После подстановки в коде просто написано `123`;
- отладчик в такие строки не войдет: отлаживать макрос бессмысленно, смотреть надо на то, во что он раскрылся (`gcc -E` в помощь);
- и наоборот: код под `#ifdef DEBUG` в релизной сборке исчезает целиком, поэтому его не будет ни в бинарнике, ни в отладчике.

Практический вывод простой. Если директива ведет себя странно, ищите ошибку в тексте, который получился после подстановки, а не в логике программы. Логика начнется позже - когда препроцессор закончит и передаст слово компилятору.
