<!-- /vscode-markdown-toc --># Системы сборки Make и CMake

##  1. <a name='1'></a>Автоматизация сборки

Про многофайловые проекты мы поговорили на теме с [библиотеками](https://github.com/kruffka/C-Programming/blob/2025-2026/12_libraries/lecture.md)                

Когда проект разрастается до десятков `.c` и `.h` файлов, собирать его вручную через `gcc` становится невозможно. Легко и быстро можно запутаться в зависимостях, а пересборка всего проекта после изменения одной строчки кода будет занимать вечность.            

Для решения этих задач существуют **системы сборки**.           
  
**Система сборки** - это инструмент, который автоматизирует превращение исходного кода в готовую программу. Вместо того чтобы вручную вводить команды для каждого файла, вы один раз описываете правила сборки в специальном конфигурационном файле.

- Обычно такая система понимает, какие файлы связаны друг с другом и если вы изменили один заголовочный файл (.h), то она сама определит, какие части проекта нужно перекомпилировать, что экономит нам время.
- Упрощает работу с библиотеками

Рассмотрим пару популярных инструментов:            

##  2. <a name='2'></a>Make  

**Make** - утилита для автоматизации процесса сборки программного обеспечения с помощью специального файла `Makefile`. Часто используется для проектов на C/C++, также можно встретить Makefile для выполнения команд в терминале (например при работе с docker). Понимает зависимости между файлами и собирает по уму, выбирая только измененные файлы                             

**Makefile** — это файл, который хранится обычно в корне проекта. Makefile состоит из набора правил, описывающих цели, зависимости и команды:    
- Цель (target): Файл, который мы хотим получить (например, исполняемый файл или объектный код), либо название действия (например, clean)
- Зависимость (prerequisite): Файлы, необходимые для создания цели. Если файл зависимости изменился, make поймет, что цель нужно пересобрать
- Команда (recipe): Конкретные действия (команды терминала), которые нужно выполнить для получения цели 

В общем виде синтаксис makefile можно представить так:  
```
цель1: реквизит1 реквизит2  
	команда1 # Важно: для отступа используется табуляция
	команда2 # команды будут выполняться последовательно и только в случае успеха предыдущей  
```
Make можно встретить как в небольших проектах, так и в огромных вроде Linux Kernel, Kubernetes или Ansible. Если в корне репозитория лежит Makefile, то вероятно, проект собирается командой `make`  

make - утилита и ее необходимо установить:
```bash
sudo apt update
sudo apt install build-essential -y
```

###  2.1. <a name='2.1'></a>Пример Makefile 1   

Рассмотрим [Пример 1](https://github.com/kruffka/C-Programming/blob/2025-2026/13_make_cmake/src/0_make/Makefile)         

```bash
main: main.o init.o utils.o
	gcc -o main main.o init.o utils.o
	
main.o: app/main.c
	gcc -c app/main.c -o main.o -I ./include

init.o: src/init.c
	gcc -c src/init.c -o init.o -I ./include

utils.o: src/utils.c
	gcc -c src/utils.c -o utils.o -I ./include

# - комментарий
# main - цель (таргет), то что хотим получить
# : main.o functions.o - зависимости, то что нам нужно, чтобы получить цель
# gcc ... - команда для получения цели
```

main, main.o, init.o и utils.o - это все разные цели. У каждой из них есть зависимости перечисленные после `:`. Если зависимости (файлы) существуют, то выполняется команда ниже. Перед командой обязательно нажимаем `TAB`, а не ставим пробелы         

Чтобы запустить перейдем в каталог с Makefile и напишем:
```bash
make
```
Увидим, что команды вывелись по порядку
```bash
gcc -c app/main.c -o main.o -I ./include
gcc -c src/init.c -o init.o -I ./include
gcc -c src/utils.c -o utils.o -I ./include
gcc -o main main.o init.o utils.o
```
Что в итоге нам дает исполняемый файл `main`            

Важно: По умолчанию make ищет `Makefile`, если он у вас называется как-то иначе, то через `-f` ключ необходимо указать путь:
```bash
make -f MyMakefile
```
Для опций можно полистать [мануал make](https://www.gnu.org/software/make/manual/make.html)            

Что еще мы можно вытворять с текущим make? Запустим его еще раз и увидим:
```bash
make: 'main' is up to date.
```
Это говорит о том, что в нашем проекте нет никаких изменений и наш исполняемый файл самый актуальный (already up to date). Попробуем поменять содержимое, например, main.c файла и снова ввести команду `make`:
```bash
gcc -c app/main.c -o main.o -I ./include
gcc -o main main.o init.o utils.o
```
Увидим, что make пересобирает лишь тот файл, в котором действительно были изменения.       
Т.е. Make понимает какие изменения были внесены в проект и знает как его собрать быстрее.         
Еще одна фишка make - можно выполнить конкретную цель, например:  
```bash
make utils.o
```

###  2.2. <a name='2.2'></a>Пример Makefile 2  
Посмотрим [пример 2](https://github.com/kruffka/C-Programming/blob/2025-2026/13_make_cmake/src/1_make/Makefile):        
```bash
.PHONY: clean # Чтобы цель clean работала даже если у нас где-то есть файл с именем clean

all: main

main: main.o init.o utils.o
	gcc -o main main.o init.o utils.o
	
main.o: app/main.c
	gcc -c app/main.c -o main.o -I ./include

init.o: src/init.c
	gcc -c src/init.c -o init.o -I ./include

utils.o: src/utils.c
	gcc -c src/utils.c -o utils.o -I ./include

clean:
	rm -rf *.o main

run: all
	./main
```
Здесь появились новые штуки:
- .PHONY
- all
- clean
- run

**all** — является стандартной целью по умолчанию, при выполнении команды `make` без опций вызовется именно она  
```bash
all: main
```
**clean** - цель, которая не имеет зависимостей, только команду:
```bash
clean:
	rm -rf *.o main
```
которая удалит все объектные файлы и исполняемый файл, полученные во время сборки. Иногда бывает удобно почистить все собранные файлы перед коммитом в гит и т.п.             
```bash   
.PHONY
```
**Phony** - с англ. фальшивый. Для того чтобы make не искал файлы с такими же именами как у целей, например clean, install и т.д., их следует определить в Makefile, при помощи директивы .PHONY. Если у нас будет где-то лежать файл с именем clean и у нас есть цель с таким же именем clean, то make clean не будет корректно отрабатывать и выполнять цель clean     

**run** - цель, что запускает исполняемый файл              

###  2.3. <a name='2.3'></a>Пример 3  
В реальных проектах никто не прописывает пути к файлам и настройки компилятора вручную в каждом правиле. Для этого используют **переменные**: [пример 3](https://github.com/kruffka/C-Programming/blob/2025-2026/13_make_cmake/src/2_make)   

Переменные позволяют хранить списки файлов, флаги оптимизации или пути к папкам. Обычно их пишут заглавными буквами. Чтобы создать переменную, пишем NAME = value, а чтобы использовать её (разыменовать) — $(NAME)           

```bash
.PHONY: clean all

CC = gcc
CFLAGS = -Wall
TARGET = main
SOURCE_DIR = src/

all: $(TARGET)

main: main.o init.o utils.o
	gcc -o main main.o init.o utils.o
	
main.o: app/main.c
	gcc -c app/main.c -o main.o -I ./include

init.o: $(SOURCE_DIR)/init.c
	gcc -c $(SOURCE_DIR)/init.c -o init.o -I ./include

utils.o: $(SOURCE_DIR)/utils.c
	gcc -c $(SOURCE_DIR)/utils.c -o utils.o -I ./include

clean:
	rm -rf *.o main
```

Также есть такое понятие как автоматические переменные (automatic variables).  
Автоматические переменные предназначены для упрощения Makefile, но негативно сказываются на их читабельности. Пример:  
- $@ - Имя цели обрабатываемого правила
- $< - Имя первой зависимости обрабатываемого правила
- $^ - Список всех зависимостей обрабатываемого правила
- % - Для генерации отдельного правила для каждого файла

[Пример с автоматическими переменными](https://github.com/kruffka/C-Programming/blob/2025-2026/13_make_cmake/src/2_make/Makefile_auto)

```bash
.PHONY: clean

CC = gcc
CFLAGS = -Wall
TARGET = main
INCLUDES = -I./include

# Цель: берем все .o файлы и линкуем в таргет
$(TARGET): main.o utils.o init.o
	$(CC) $(CFLAGS) $^ -o $@
# $@ заменится на main
# $^ заменится на main.o utils.o init.o

# Универсальное правило для объектных файлов
# % - создаем шаблон для каждого файла
%.o: src/%.c
	$(CC) $(CFLAGS) $(INCLUDES) -c $< -o $@
# % — это паттерн (имя файла)
# $< — это конкретный .c файл (первая зависимость)
# $@ — имя конкретного .o файла (цель)

%.o: app/%.c
	$(CC) $(CFLAGS) $(INCLUDES) -c $< -o $@
	
clean:
	rm -rf *.o $(TARGET)
```

Для запуска:
```bash
make -f Makefile_auto
```

Утилита make содержит много опций, одна из полезных - это опция для ускорения сборки проекта "-j" - данной опцией мы говорим сколько потоков забрать для сборки проекта.                 
Например make -j8 - сборка с 8 потоками одновременно (параллельная сборка возможно благодаря независимости различных целей и компиляции их в объектные файлы) и многоядеронсти процессора.        

Makefile используется не только для сборки проектов, но и для выполнения команд в командной строке, например для докера. Это такая штука, работающая с виртуальными машинами и чтобы не прописывать различные докер команды и опции можно их описать в Makefile в виде правил up и скажем down - означающее подними (up) все виртуальные машины или потуши (выключи - down) все виртуальные машины при обращении к ним через make up, make down соответственно

```bash
# Поднять окружение в фоновом режиме
up:
	docker-compose up -d

# Остановить и удалить контейнеры, сети и образы
down:
	docker-compose down

# Посмотреть логи приложения
logs:
	docker logs -f my_container_name
```

В Embedded разработке, например микроконтроллеров (STM32, AVR, ESP32) Makefile - это сердце проекта. В нем описывается сборка, конфигурация (частоты проца например), различные флаги и даже цели с правилами прошивки железок. Тоесть Makefile - такой универсальный клей, что связывает код, компилятор и прочие инструменты для работы в единую рабочую среду               

Но как бы make не упрощал жизнь, все равно приходится писать команды компиляции руками.. поэтому на помощь приходит CMake     

##  3. <a name='3'></a>CMake  

**CMake** - кроcсплатформенная утилита для автоматической сборки программы из исходного кода. Если Make - это список команд для компилятора, то CMake - это инструмент более высокого уровня. Он не заменяет Make, а стоит над ним. Он работает с файлами по фамилии `CMakeLists.txt`, в которых на языке CMake описывается конфигурация и сборка проекта. Далее CMake генерит готовый к использованию Makefile

**Важно:** CMake не собирает проект, а лишь конфигурит и генерит Makefile, который уже собирает проект.

Функций в cmake очень-очень много и с каждой новой версией появляется все больше фич - все я здесь не буду описывать, лишь те, что жизненно необходимы, поэтому оставлю здесь ссылку покурить [CMake мануал](https://cmake.org/cmake/help/latest/guide/tutorial/index.html)          
Еще примеры и почитать дополительно [Введение в CMake (хабр)](https://habr.com/ru/articles/155467/)    
[ИТМО wiki CMake](https://neerc.ifmo.ru/wiki/index.php?title=CMake_Tutorial)        

Установить CMake:               
```bash
sudo apt update
sudo apt install build-essential cmake -y 
```

###  3.1. <a name='3.1'></a>Пример CMakeLists.txt 1  

Посмотрим на все тот же маленький проект из нескольких файлов, но с CMake: [Пример 1](https://github.com/kruffka/C-Programming/blob/2025-2026/13_make_cmake/src/cmake_0/CMakeLists.txt)          

В отличие от Make, который мусорит объектными файлами прямо рядом с исходниками, в CMake принят стандарт собирать проект вне папки с исходниками.
Все временные файлы живут в папке `build`, которую можно удалить одной командой, не боясь зацепить важный код. Классический способ собрать типовой проект, использующий CMake (внутри склонированного проекта):
```bash
mkdir build && cd build
cmake ..
make
```
- Создаем каталог build и заходим в него
- Вызываем утилиту cmake для генерации Makefile и прописываем через пробел путь до CMakeLists.txt (.. - две точки означает на каталог выше, т.е. в предыдущей папке)
- Собираем проект с помощью make         

Эта инструкция из нескольких шагов встречается повсеместно и ее необходимо запомнить и понять            

Либо тоже самое двумя командами, используя лишь cmake (так нынче модно и современно):   
```bash
cmake -B build
cmake --build build
```

**Важно:** **CMake** вызывается единожды для конфигурации Makefile, далее при изменении исходник мы вызываем только **make**! **CMake** повторно имеет смысл вызывать если что-то меняется в самом CMakeLists.txt              


Рассмотрим теперь само содержимое и синтаксис CMake файла CMakeLists.txt:   
```bash
# Я комментарий
# Задаем планку версии. Если у разработчика CMake старее — он увидит ошибку
cmake_minimum_required(VERSION 3.10)

# Инициализирует проект и создает полезные переменные типа ${CMAKE_CURRENT_SOURCE_DIR},
# что означает текущий каталог с исходниками
project(hello_cmake)

# Создание переменных APP_DIR и SOURCE_DIR
set(APP_DIR ${CMAKE_CURRENT_SOURCE_DIR}/app)

set(SOURCE_DIR ${CMAKE_CURRENT_SOURCE_DIR}/src)
set(SOURCES 
    ${SOURCE_DIR}/utils.c
    ${SOURCE_DIR}/init.c
)

# Аналог опции -I
include_directories(${CMAKE_CURRENT_SOURCE_DIR}/include)

# Главная цель: что собрать и из чего.
# Формат: add_executable(ИМЯ_ПРОГРАММЫ ИСХОДНИКИ)
add_executable(main ${APP_DIR}/main.c ${SOURCES})
```
Комментарии здесь как и в Makefile начинаются с #. Многострочные в `#[[ комментарий ]]`        
  
```bash
cmake_minimum_required(VERSION x.xx)
```
Здесь мы задаем «нижний порог» версии CMake. Это важно, так как в новых версиях постоянно появляются полезные фичи, и если проект использует функции версии 3.20, он просто не соберется на старом софте.

```bash
project(hello_cmake)
```
Команда `project()` делает сразу несколько полезных вещей:
- Устанавливает имя проекта (оно сохранится в переменной ${PROJECT_NAME}).
- Инициализирует переменные путей:
  - **PROJECT_SOURCE_DIR** — абсолютный путь к папке, где лежит ваш CMakeLists.txt (исходники).
  - **PROJECT_BINARY_DIR** — абсолютный путь к папке, где происходит сборка (обычно это папка build). Именно здесь будут лежать скомпилированные файлы.

Переменные устанавливаются через set, а разыменовываются через `${MY_VARIABLE}`
```bash
set(APP_DIR ${CMAKE_CURRENT_SOURCE_DIR}/app)
```

```bash
add_executable(main ${APP_DIR}/main.c ${SOURCES})
```
Это цель сборки. Функция сообщает системе: "Я хочу получить исполняемый файл с именем main, собрав его из списка исходников (что лежат в переменной `${SOURCES}`)"       

**Полезно:** CMake хранит результаты проверок системы (пути к компиляторам, найденные пакеты) в файле CMakeCache.txt. Если вы что-то кардинально поменяли в системе и сборка "сломалась", то удалите этот файл (или всю папку build) и запустите cmake .. заново.       

**Самостоятельно:** поглядеть на сгенеренный Makefile, там даже есть цель help        

###  3.2. <a name='3.2'></a>Пример CMakeLists.txt 2    

Усложняем библиотеками: [Пример 2](https://github.com/kruffka/C-Programming/blob/2025-2026/13_make_cmake/src/cmake_1/CMakeLists.txt)   
```bash
cmake_minimum_required(VERSION 3.10)

project(hello_cmake)

set(APP_DIR ${CMAKE_CURRENT_SOURCE_DIR}/app)

set(SOURCE_DIR ${CMAKE_CURRENT_SOURCE_DIR}/src)
set(SOURCES 
    ${SOURCE_DIR}/utils.c
    ${SOURCE_DIR}/init.c
)
include_directories(${CMAKE_CURRENT_SOURCE_DIR}/include)

# Сборка библиотеки
add_library(UTIL_LIB STATIC ${SOURCES}) 
# Статическая библиотека STATIC
# Для динамических SHARED, для "плагин" библиотек - MODULE

add_executable(main ${APP_DIR}/main.c)
target_link_libraries(main UTIL_LIB) # Линковка

```
Из нового здесь - это библиотеки и их линковка. Чтобы собрать **статическую библиотеку** используем слово **STATIC** в `add_library()`, для **динамической SHARED**. Для линковки - `target_link_libraries()`.        

###  3.3. <a name='3.3'></a>Пример 3   

Посмотрим проект, состоящий из нескольких CMakeLists.txt [Пример 3](https://github.com/kruffka/C-Programming/blob/2025-2026/13_make_cmake/src/cmake_2/CMakeLists.txt)     

Корневой CMakeLists.txt:
```bash
cmake_minimum_required(VERSION 3.10) 	# Проверка версии CMake.
										# Если версия установленой программы
										# старее указаной, произойдёт аварийный выход.

project(hello_cmake)					# Название проекта

set(SOURCE_EXE main.c)					# Установка переменной со списком исходников

include_directories("./subdir")			# Расположение заголовочных файлов

add_executable(main ${SOURCE_EXE})		# Создает исполняемый файл с именем main

add_subdirectory("./subdir")			# Добавление подпроекта, указывается имя дирректории

add_definitions("-DTEST_DEF=5")			# Аналогично обьявлению в коде #define TEST_DEF 5

target_link_libraries(main MY_LIB)		# Линковка программы с библиотекой
```
Пойдем почти порядку.  
include_directories() - используется для указанию компилятору подобно опции -I пути до заголовочных файлов, чтобы в исходниках в директивах #include не прописывать полные пути до заголовочников.   
add_definitions() - аналог #define в Си и опции -D при компиляции через gcc, мы определяем так некоторые #define для условной компиляции. Например, тот же DEBUG для отладки.      

Следующая вещь полезна когда идет речь о многофайловых проектах, содержащих множество поддиректорий и это:    
add_subdirectory() - указываем путь до CMakeLists.txt находящегося где-то внутри проекта для сборки некоторого отдельного модуля. Вызвав данную функцию cmake нырнет в эту поддиректорию и начнет выполнять оттуда CMakeLists.txt, в котором у нас следующее содержимое:   
```bash
set(SOURCE_LIB functions.c)	
add_library(MY_LIB SHARED ${SOURCE_LIB})	# Создание дин. библиотеки с именем MY_LIB
```

Некоторые часто используемые переменные в CMake:    
CMAKE_BUILD_TYPE: Типичные значения включают Debug, Release, RelWithDebInfoи MinSizeRel, но также можно определить свои типы сборки.   
1. Release: Высокий уровень оптимизации, без отладочной информации.  
2. Debug: Без оптимизаций, содержит отладочную информацию для дебага.  
3. RelWithDebInfo: Оптимизирован, но содержит отладочную инфу.  
4. MinSizeRel: Тоже что и Release, но оптимизация здесь заключается в размере файла, чем в скорости.  

Если говорить как компилятор, то флаги будут примерно следующие:    
1. Release: `-O3 -DNDEBUG`  
2. Debug: `-O0 -g`  
3. RelWithDebInfo: `-O2 -g -DNDEBUG`  
4. MinSizeRel: `-Os -DNDEBUG`  
Где определение NDEBUG добавляется к платформам, поддерживающим это (отключает например assert()).   

Переменные в cmake можно присвоить двумя способами, первый через set присвоить в CMakeLists.txt:  
```bash
set(CMAKE_BUILD_TYPE Release)
```
и второй через опцию при вызове cmake:      
```bash
cmake .. -DCMAKE_BUILD_TYPE=Release
```

Так можно придумать способ определения некоторых констант, например воспользуемся условиями в cmake (if() endif()).  
```bash  
if (${TEST_DEF})  
	add_definitions("-DTEST_DEF=${TEST_DEF}")   
endif()  
```  
Как пользоваться такой конструкцией? просто пишем после переменную через -D:  
```bash
cmake .. -DTEST_DEF=123
```
Эта запись создаст переменную в cmake и внутри CMakeLists.txt отработает условие и добавится определение TEST_DEF в наш код. При запуске кода увидим новый printf() с test_def равным 123.

## 4. <a name='4'></a>Ninja

Если проект становится по-настоящему огромным (как браузер Chrome или Android), классический make может начать подтормаживать. Для таких случаев существует Ninja
Ninja - это быстрая и легковесная система сборки, созданная в Google.           

Ninja создана для того, чтобы запускать компиляцию файлов максимально параллельно и без задержек. Файлы для Ninja (с расширением .ninja) почти нереально писать вручную - они выглядят как машинный код. Предполагается, что их будет генерировать CMake.       

Чтобы его использовать не нужно учить новый синтаксис, достаточно его установить:
```bash
sudo apt update
sudo apt install ninja-build
```
и сказать CMake используй Ninja в качестве движка:
```bash
cmake -G Ninja -B build
cmake --build build
```
[Ссылка на ninja](https://github.com/ninja-build/ninja)
